# Database migrations (Alembic)

**This is optional tooling, not a required deploy step.** `app/db.py`'s
`init_db()` already creates a fresh database and upgrades an existing one
(additive column/index changes, backfills) automatically at every app
startup -- see the README's "Deployment" and "Multi-site" sections. A
normal deployment never needs to touch this directory or run an `alembic`
command; `pip install -r requirements.txt` (not `requirements-migrations.txt`)
is enough.

Alembic exists here for the migrations `init_db()`'s own approach
structurally can't do safely: renaming or dropping a column, changing a
column's type, splitting one table into two, or a real data migration
(transforming existing rows, not just adding a column with a default).
SQLite and PostgreSQL can't portably do those as a single `ALTER TABLE`
the way `init_db()`'s column-diffing migrator adds a column, so they need
a real migration script, reviewed and tested like any other code change,
rather than an automatic startup step.

## Setup

```bash
pip install -r requirements-migrations.txt
```

`migrations/env.py` reads the target database from `DRONE_DATABASE_URL`
(via `app.config.DATABASE_URL`) and the schema from `app.schema.metadata`
-- the same `MetaData` object `init_db()` itself uses -- so there's one
source of truth for both "which database" and "what the schema should
look like," not a second copy that can drift from the first.

## Baseline

`migrations/versions/`'s first revision is a baseline capturing the
schema as of this feature's introduction (the full multi-site-era
schema) -- autogenerated against an empty database and verified
byte-for-byte identical (via `alembic check`) to what `init_db()` itself
creates from scratch, on both SQLite and PostgreSQL. It's not meant to
ever run against a database that already has this app's tables in it
(that database was built by `init_db()`, not Alembic, and already has
everything the baseline would create) -- stamp it instead:

```bash
alembic stamp head
```

That records "this database is at the baseline revision" without running
any DDL, so `alembic history`/`alembic current` have something real to
compare future revisions against. Only a genuinely fresh, empty database
should ever run `alembic upgrade head` for the baseline itself.

## Adding a real migration

For the non-additive changes described above:

```bash
# 1. Change app/schema.py first -- it's still the single source of truth.
# 2. Autogenerate a draft against a database at the current baseline:
alembic revision --autogenerate -m "describe the change"
# 3. Read the generated file. Autogenerate detects structural diffs but
#    not data migrations (e.g. splitting a column's values into a new
#    column) -- write those by hand in the same revision.
# 4. Test it both directions against a disposable database:
alembic upgrade head
alembic downgrade -1
alembic upgrade head
```

Then apply it to a real deployment's database with `alembic upgrade
head` as an explicit, deliberate deploy step -- unlike `init_db()`'s
additive changes, this kind of migration should never run silently and
automatically at app startup.
